# plans/ — технические планы

Один план = одна функция или один трек работ. Файл: `plans/YYYY-MM-DD-название.md` по [TEMPLATE.md](TEMPLATE.md).

## Зачем

Треки (A–D, E1, E1b/E2/E3) раньше жили только в памяти агента и в голове. Файл плана нужен ровно для одного: чтобы через месяц было видно, **где трек оборвался и что осталось**. За это отвечает секция «Итог» в конце шаблона — она заполняется в конце работы, а не в начале.

## Цикл

1. `superpowers:brainstorming` — до того как писать план.
2. `superpowers:writing-plans` — пишет план в этот каталог.
3. Опционально критика: `prompts/10-reasons.md` перед крупным шагом (merge в main, запуск монетизации, деплой на прод).
4. `superpowers:executing-plans` — реализация по фазам, статусы `[ ]` / `[x]` актуализируются после каждой сессии.
5. `superpowers:verification-before-completion` — перед тем как объявить фазу закрытой. Для этого проекта верификация = `python -m pytest -q` целиком, а не только новые тесты.
6. Заполнить «Итог», завести ретро в `../retrospectives/`.

## Правила

- Фаза без критерия готовности — не фаза. «Работает» не критерий, «`pytest -q` зелёный + импорт `main` проходит» — критерий.
- Что всплыло, но не входит в план, — в «Открытые вопросы», а не в код по ходу дела.
- Архитектурные решения из плана, которые переживут сам план, переезжают в `docs/architecture/` как ADR.
